# Spec: AI Chat Search Accuracy, Context Retention & Offer Filtering

- **Spec**: [#221](https://github.com/MickRheault/rv2/issues/221)
- **Issue**: [#219](https://github.com/MickRheault/rv2/issues/219)
- **ADR**: [ADR 0020](../adr/0020-chat-filter-resolution-and-offer-search-semantics.md)
- **Date**: 2026-11-11

## Problem Statement

Riders using RideVault's AI chat assistant to discover rental shops and motorcycle inventory experience false-negative answers, lost follow-up context, missing rental terms, currency-confused price filtering, truncated responses, and conflation of catalog presence with live date availability (#219):

1. **Multi-turn context loss**: Each follow-up message sent from the chat UI omits prior conversation turns, causing the assistant to forget the city, shop, motorcycle, or rental window established moments earlier (for example, replying `"In Chiang Mai"` after `"Where can I rent a Honda ADV 160?"` or asking `"What are their opening hours?"` after discussing a specific shop).
2. **False negatives on published Catalog Listings**: Searching by a shop name (`"Riders Corner"`), a combined brand-and-model phrase (`"BMW F 800 GS"`, `"Detech Win"`, `"Honda Air Blade"`), model spacing/punctuation variants (`"F800GS"`, `"CRF 250"`), localized or comma-qualified city names (`"Roma"`, `"Rome, Italy"`, `"Ha Noi"`, `"Saigon"`), or popular models without a city filter (capped at the newest 10–20 rows without pagination or shop filtering) returns zero matching rows or misses matching shops, causing the assistant to tell riders that live published shops or motorcycles are not listed on RideVault.
3. **Silent filter dropping & regional prompt bias**: When an explicit city, country, brand, or category filter fails to match a catalog record, the internal tool layer silently drops the unresolved filter and returns unrelated global results while the system prompt still frames RideVault as a Southeast Asia–only assistant despite active European inventory (such as Rome and Barcelona).
4. **Missing shop opening hours & motorcycle rental conditions alongside bloated tool payloads**: Internal chat lookups omit published shop conditions (such as opening hours stored in structured shop conditions) when fetching a shop by ID, omit per-motorcycle conditions (such as deposit amounts and helmet policies) from motorcycle search and shop fleet summaries, and serialize entire destination editorial articles inside shop and motorcycle detail tool responses.
5. **Currency-blind & single-day-only price filtering**: Daily price range filters compare numeric amounts without checking currency (mixing `7–9 USD/day` and `150,000–220,000 VND/day` listings in the same city), evaluate only the shortest-duration standalone daily bracket (ignoring multi-day daily brackets such as `7+ days` and fixed-day package Daily Equivalents when a rider asks for a multi-day or 30-day budget), and lack an explicit filter to exclude `"Price on request"` listings.
6. **Mid-sentence / mid-link output truncation**: A strict 500-token completion ceiling combined with no handling for length-stopped model completions cuts multi-listing answers off mid-sentence or mid-markdown link.
7. **Catalog Listing vs. live date availability conflation**: When riders ask about specific travel dates (for example, `"next weekend"`), the assistant lacks explicit domain guidance separating published **Catalog Listings** from live, date-specific booking availability.

## Solution

Deliver end-to-end accuracy, stateful multi-turn context, structured rental terms, and currency/duration-aware **Rental Offer** filtering across RideVault's AI chat UI, chat API, internal chat tools, and shared search services:

1. **Stateful Multi-Turn Chat & Truncation Resilience**: Send bounded prior conversation history from the chat interface on every follow-up turn, expand history per-message and completion token budgets so multi-listing turns survive intact while keeping prompt-abuse and rate-limit protections active, cap default per-turn listings to a scannable set with total match counts and pagination cues, and add a server-side completion-length safeguard that trims broken trailing markdown links/fragments and appends a clean continuation prompt whenever generation stops on token length.
2. **Global Guardrails & Catalog Listing Vocabulary**: Define **Catalog Listing** in the domain glossary, remove Southeast Asia–only framing from the chat prompt in favor of global RideVault catalog coverage, require explicit separation between published catalog presence and unconfirmed live date availability, and forbid definitive `"not listed"` claims after a single narrow zero-result tool call.
3. **Shop Filtering, Brand/Model/Location Normalization & Explicit Unresolved Filter Reporting**: Add shop filtering (by shop name or identifier) and pagination offset support to motorcycle search tools, normalize `"City, Country"` inputs, diacritics, common city aliases, combined `"Brand Model"` queries, and spacing/punctuation model variants against **Canonical Model Names**, and return explicit `unresolvedFilters` metadata with zero results whenever an explicit location, shop, brand, or category filter still cannot be resolved—never silently dropping a user's filter.
4. **Structured Shop Hours, Motorcycle Conditions & Lean Tool Payloads**: Include structured shop conditions (including opening hours) when loading shops by ID, surface concise structured conditions and inclusions summaries (opening hours, deposit amounts, helmet policies, license/gear terms) across shop and motorcycle chat tool responses, and strip destination editorial content sections from tool payloads so context budget goes to actionable rental data.
5. **Currency, Rental Duration & Known-Price Offer Filtering**: Extend **Rental Offer** filtering ([ADR 0018](../adr/0018-flexible-rental-offers-and-legacy-daily-projection.md)) with optional ISO `currency`, `durationDays`, and `knownPriceOnly` filters across offer evaluation helpers, motorcycle search services, public REST search, and internal chat tools—matching currency strictly when specified, evaluating the applicable standalone `daily` bracket or exact-duration fixed-day `package` **Daily Equivalent** when `durationDays` is provided (without ever dividing `calendar_month` offers by 30), and always excluding `"Price on request"` listings when price bounds or `knownPriceOnly` are requested.

## User Stories

1. As a rider asking a follow-up question in AI chat (such as `"In Chiang Mai"` after `"Where can I rent a Honda ADV 160?"`), I want the assistant to retain my previous turns, so that it narrows the search to Honda ADV 160 listings in Chiang Mai instead of forgetting which motorcycle I asked about.
2. As a rider asking sequential questions about a shop or motorcycle (`"What bikes does Riders Corner have?"` followed by `"What are their opening hours?"` or `"Which one has the lowest deposit?"`), I want prior assistant and user turns preserved with enough detail to reference previously listed motorcycles and shops, so that follow-up questions resolve naturally without repeating full names.
3. As a rider starting a chat via a deep-linked query URL parameter, I want the initial prompt submitted cleanly and included in subsequent follow-up history, so that multi-turn conversations started from homepage or search shortcuts work identically to typed sessions.
4. As a rider encountering a transient network or rate-limit error in chat, I want error banner messages excluded from subsequent conversation history payloads, so that synthetic UI error text does not pollute future assistant turns.
5. As a rider searching for motorcycles in Rome, Barcelona, or any other region in RideVault's catalog, I want the assistant to search and present global **Catalog Listings** accurately, so that European or non-Asian destinations are never dismissed as outside RideVault's scope.
6. As a rider typing `"Roma"` or `"Rome, Italy"`, `"Ha Noi"`, or `"Saigon"`, I want location resolution to normalize comma-appended country qualifiers, diacritics, and common city aliases, so that my city filter resolves to the canonical RideVault city record.
7. As a rider asking about a destination or brand that truly does not exist in RideVault's catalog (such as `"motorcycles in Atlantis"` or an unlisted brand), I want the search tool to report the unresolved filter explicitly with zero results instead of silently dropping the filter, so that the assistant tells me no matching listings were found rather than presenting unrelated motorcycles from other cities or brands.
8. As a rider asking `"Does Riders Corner in Chiang Mai have a Honda ADV 160?"` or `"What motorcycles are available at Bike Phuket Garage?"`, I want the assistant to filter motorcycle listings directly by shop name or shop ID and paginate beyond the first 10 global results, so that popular models at a specific shop are found immediately regardless of global fleet size.
9. As a rider searching with a combined brand-and-model phrase such as `"BMW F 800 GS"`, `"Detech Win"`, or `"Honda Air Blade"`, I want search normalization to recognize the brand prefix and match the **Canonical Model Name**, so that including the manufacturer name never causes a zero-hit false negative.
10. As a rider typing model names with compact or varied spacing/punctuation such as `"F800GS"`, `"F-800-GS"`, `"CRF 250"`, or `"ADV160"`, I want model search to match spacing- and hyphen-normalized **Canonical Model Names** (`"F 800 GS"`, `"CRF250"`, `"ADV 160"`), so that minor formatting differences still return every matching listing.
11. As a rider asking about a specific shop or motorcycle when an initial narrow query returns zero hits, I want the assistant to verify via broader shop or catalog lookup before concluding a shop or listing is absent, so that I do not receive false `"not listed on Global Moto Rentals (GMR)"` answers for published inventory.
12. As a rider asking `"What are the opening hours for Riders Corner?"`, I want shop lookups by ID and slug alike to return structured shop conditions including opening hours, so that the assistant can state exact published operating hours when recorded in the catalog.
13. As a rider asking `"What is the deposit and helmet policy for the Honda ADV 150 ABS at Bike Phuket Garage?"`, I want motorcycle search results, shop fleet listings, and motorcycle detail lookups to expose structured per-motorcycle conditions and shop inclusions, so that deposit amounts, helmet policies, and rental requirements are answered directly from catalog data.
14. As an operator running the AI chat service, I want internal shop and motorcycle tool responses to omit bulky destination editorial markdown sections while keeping actionable shop, fleet, offer, inclusion, and condition fields, so that multi-bike tool calls stay fast, compact, and within model context limits.
15. As a rider asking `"Find me a scooter in Hanoi under 10 USD per day"`, I want price filtering to enforce the `USD` currency code strictly, so that `150,000 VND/day` listings are not excluded or miscompared against a `10` numeric threshold and `7–9 USD/day` listings are returned accurately.
16. As a rider asking `"Show me motorcycles in Chiang Mai under 350 THB/day for a 7-day rental"` or `"for 30 days"`, I want duration-aware price filtering to evaluate the applicable standalone `daily` bracket covering 7 or 30 days (as well as exact-duration fixed-day `package` **Daily Equivalents** matching that duration), so that multi-day discounts and weekly/30-day packages are matched accurately without inventing synthetic daily rates from calendar-month offers.
17. As a rider asking only for motorcycles with published prices (or specifying a minimum/maximum budget), I want `"Price on request"` listings excluded whenever `minPrice`, `maxPrice`, or `knownPriceOnly` is active, so that unpriced inventory never clutters budget-filtered results.
18. As a rider browsing a city with dozens of matching motorcycles in chat, I want the assistant to present up to 6 complete listings with valid links, prices, and key terms, state the total number of matches found, and offer to show more, so that responses remain readable and fit cleanly within a single turn.
19. As a rider receiving a long chat answer that hits the model output token ceiling, I want the server to strip any half-written trailing markdown link or sentence fragment and append a clear continuation note, so that I never see broken URLs or cut-off words in the chat UI.
20. As a rider asking `"Can I rent a BMW F 800 GS in Rome next weekend?"`, I want the assistant to confirm the published **Catalog Listing**, shop, and pricing on RideVault while clearly noting that live date-specific booking availability is not tracked in real time and providing the listing/shop link to confirm dates directly with the shop.

## Implementation Decisions

1. **Domain Glossary Addition (`Catalog Listing`)**:
   - Define **Catalog Listing** in the domain glossary as a published rental shop profile or active motorcycle inventory record (`available` status) curated in RideVault with supplier-stated **Rental Offers**, inclusions, and conditions—explicitly distinct from live, date-specific fleet stock or real-time booking availability.
2. **ADR 0020 — Explicit Chat Filter Resolution & Currency/Duration-Scoped Offer Filtering (Extends ADR 0018)**:
   - Record an Architecture Decision Record capturing two deliberate contracts:
     1. Internal chat search tools normalize common human query inputs (`"City, Country"`, diacritics, curated city aliases, `"Brand Model"` combinations, and spacing/punctuation model variants), and when any explicit entity filter (`city`, `country`, `countryCode`, `shop`, `brand`, `category`) still fails to resolve, return zero rows alongside structured `unresolvedFilters` metadata rather than silently dropping the unresolved constraint.
     2. Price range filtering preserves ADR 0018's standalone-daily default when `durationDays` is omitted, requires an exact ISO currency match when `currency` is supplied, evaluates only the applicable `daily` bracket covering `durationDays` plus exact-duration fixed-day `package` **Daily Equivalents** (`duration_unit = 'day'`, fixed `days > 1`: `durationDays > 1 && min_duration === durationDays && max_duration === durationDays`) when `durationDays` is supplied—never dividing `calendar_month` offers by 30 or extrapolating unquoted durations—and excludes unpriced listings whenever `minPrice`, `maxPrice`, or `knownPriceOnly` is active.
3. **Stateful Multi-Turn Chat Client & History Sanitization**:
   - Update the chat client so every follow-up submission includes bounded `conversationHistory` built from prior completed `user` and `assistant` turns in chronological order, excluding the outgoing prompt itself, unanswered failed `user` prompts, and client-side error placeholder messages.
   - Keep `MAX_MESSAGE_LENGTH = 500`, `MAX_HISTORY_MESSAGES = 10`, the anti-repetition user-input pre-filter, `system`-role message stripping, tool-round caps, and the 20-requests-per-hour IP rate limit intact.
   - Increase `MAX_HISTORY_MESSAGE_LENGTH` from `1000` to `2500` characters so multi-listing assistant responses retain motorcycle names, shop names, and relative markdown links across follow-up turns.
4. **Output Token Budget, Truncation Guard & Prompt Guardrails**:
   - Increase `MAX_OUTPUT_TOKENS` from `500` to `1200` tokens.
   - Add a deterministic post-processing safeguard on chat completions: when the model's finish reason is `'length'`, trim any incomplete trailing markdown link (`[label](/incomplete...`) or unfinished trailing sentence/line and append a concise continuation prompt inviting the user to ask for more results or details.
   - Revise the chat system prompt to:
     - Describe Global Moto Rentals (GMR) / RideVault as a global motorcycle rental catalog rather than Southeast Asia–only.
     - Instruct the model to display up to 6 complete motorcycle or shop results per turn when a search returns larger sets, mention the total match count, and offer to show additional results using pagination (`offset`) or narrower filters.
     - Enforce the **Catalog Listing** boundary: confirm published catalog listings, pricing, and rental terms, while explicitly stating that live date-specific stock/booking availability is not verified in real time and linking the rider to the listing/shop page to confirm dates.
     - Require broadening or cross-checking (for example, checking the shop profile or searching by brand/city) before claiming a shop or motorcycle is not listed when a narrow query returns zero hits, and require honoring `unresolvedFilters` honestly when a location, shop, brand, or category does not exist in the catalog.
5. **Filter Normalization, Shop Filtering & Pagination in Search Services and Chat Tools**:
   - Add optional `shop` (accepting either a shop UUID or a shop name/slug query) and `offset` (non-negative integer, default `0`) parameters to the internal `list_motorcycles` tool and underlying motorcycle search service.
   - Normalize location strings before resolution by stripping diacritics, splitting `"City, Country"` inputs (using the country qualifier to disambiguate or validate when present), and mapping curated aliases (`Roma` → `Rome`, `Ha Noi` → `Hanoi`, `Saigon` / `HCMC` → `Ho Chi Minh City`, `Phuket Town` / `Phuket`, `Chiangmai` → `Chiang Mai`, `Danang` → `Da Nang`).
   - Normalize free-text motorcycle `query` / `model` inputs by:
     - Detecting leading brand names/slugs against the catalog brand list when `brand` was not separately resolved (splitting `"BMW F 800 GS"` into brand `BMW` + model `"F 800 GS"`, and `"Detech Win"` into brand `Detech` + model `"Win"`).
     - Matching model names insensitively across spaces and hyphens so `"F800GS"`, `"F-800-GS"`, and `"F 800 GS"` (or `"CRF 250"` and `"CRF250"`, `"ADV160"` and `"ADV 160"`) match the same **Canonical Model Name** records without requiring database schema migrations.
   - Replace silent filter dropping in `list_motorcycles` and `list_shops`: if any caller-supplied entity filter (`city`, `country`, `countryCode`, `shop`, `brand`, `category`) cannot be resolved, return an empty result set (`total: 0`) plus `unresolvedFilters: Array<{ filter: string; value: string }>` immediately instead of running an broader unfiltered query.
6. **Structured Conditions, Shop Hours & Lean Tool Payloads**:
   - Update shop-by-ID retrieval in the shop service so it selects structured `rental_shop_conditions` joined with `condition_types`—matching the existing shop-by-location-and-slug query—so opening hours and shop rental policies are present regardless of how a shop is fetched.
   - Select per-motorcycle `conditions_details` and structured `motorcycle_conditions` joined with `condition_types` in motorcycle listing and shop fleet queries used by chat tools.
   - Format concise, human-readable `conditions` and `inclusions` arrays/summaries on internal `list_motorcycles`, `get_motorcycle`, `list_shops`, and `get_shop` tool outputs (surfacing opening hours, deposit amounts, helmet policies, minimum age/license rules, and included gear).
   - Strip heavy destination editorial fields (such as nested `countries.content_sections`) from internal `get_shop` and `get_motorcycle` tool responses while keeping public page rendering untouched.
7. **Currency, Duration & Known-Price Rental Offer Filtering**:
   - Extend offer filter options and motorcycle search filters with three optional parameters across the offer evaluation module, motorcycle search service, `GET /api/v1/motorcycles`, and internal `list_motorcycles`:
     - `currency`: optional 3-letter uppercase ISO currency code (case-insensitively normalized, e.g. `usd` → `USD`). When provided, a motorcycle matches price/known-price filters only via offers whose `currency` equals the requested code (or legacy daily tiers/projected rate matching the motorcycle's normalized currency when no `rental_offers` rows exist).
     - `durationDays`: optional positive integer (`>= 1`). When omitted, preserve ADR 0018's default (evaluate standalone `daily` offers). When provided, evaluate:
       1. Standalone `daily` offers (`offer_type = 'daily'`, `billing_basis = 'per_day'`, `duration_unit = 'day'`) whose duration bracket covers `durationDays` (`(min_duration ?? 1) <= durationDays` and `(max_duration === null || max_duration >= durationDays)`), falling back to the open-ended or highest applicable daily bracket only when its range covers `durationDays`; and
       2. Fixed-day `package` offers (`offer_type = 'package'`, `billing_basis = 'package_total'`, `duration_unit = 'day'`, fixed `days > 1`) whose fixed duration equals `durationDays` (`durationDays > 1 && min_duration === durationDays && max_duration === durationDays`), compared via their deterministic **Daily Equivalent** (`round(amount / durationDays, 2)`).
       - Never convert `calendar_month` offers (`per_calendar_month` or `duration_unit = 'calendar_month'`), `hourly` offers, or `extension` charges into daily rates.
     - `knownPriceOnly`: optional boolean. When `true` (or whenever `minPrice` or `maxPrice` is specified), exclude `"Price on request"` motorcycles that have no qualifying priced offer (and, when `currency` is also specified without `minPrice`/`maxPrice`, require at least one published priced offer in that currency).

## Testing Decisions

- **What makes a good test**: Assert observable inputs and outputs at public UI, route, tool, and service boundaries—verifying request bodies, HTTP status codes, returned JSON structures, matched/excluded listings, and user-visible text—without coupling to private helper names or internal Supabase query builder call order where higher seams exist.
- **Three Verification Seams**:
  1. **Chat UI & API Route Seam** (following existing chat page and chat route unit/integration tests):
     - Verifies multi-turn `conversationHistory` transmission across sequential prompts and `?q=` initial prompts, exclusion of error banners from history, `2500`-char per-history-message truncation, `1200` `max_completion_tokens`, `finish_reason === 'length'` trailing-link cleanup and continuation notice, global system prompt guardrails, and preservation of all `#190` anti-abuse/rate-limit protections.
  2. **Internal MCP Tool Execution Seam** (following existing internal chat tool tests):
     - Verifies `list_motorcycles`, `get_motorcycle`, `list_shops`, and `get_shop` behavior for `shop` and `offset` parameters, `"City, Country"` and alias resolution (`Roma`, `Ha Noi`, `Saigon`), `"Brand Model"` splitting (`BMW F 800 GS`, `Detech Win`), spacing-insensitive model matching (`F800GS`, `CRF 250`), explicit `unresolvedFilters` zero-result responses without silent filter drops, structured opening hours/deposit/helmet condition summaries, stripped `content_sections` payloads, and `currency`/`durationDays`/`knownPriceOnly` tool forwarding.
  3. **Search Service, REST Route & Rental Offer Filter Seam** (following existing motorcycle filter, shop service, and rental offer unit tests):
     - Verifies `shopService.getShopById` returning `rental_shop_conditions`, `GET /api/v1/motorcycles` query validation and forwarding for `currency`, `durationDays`, `knownPriceOnly`, and `shopId`, strict ISO currency matching (`USD` vs `VND` vs `THB`), duration-bracket selection (`1` day vs `7` days vs `30` days), exact-duration fixed-day `package` **Daily Equivalent** matching, strict non-conversion of `calendar_month` offers, and exclusion of `"Price on request"` rows under price or `knownPriceOnly` filters.

## Out of Scope

- Live inventory calendars, real-time booking engines, date-range availability reservations, or supplier availability webhooks.
- Automatic FX / exchange-rate conversion across currencies (price filters compare verbatim supplier currencies rather than converting `VND` to `USD` via fluctuating exchange rates).
- Server-persisted user chat accounts or cross-device chat history storage in Supabase (conversation state remains client-session scoped).
- External/admin write MCP server tools (`create_motorcycle`, `update_shop`, etc.)—this spec applies to the public rider discovery & AI chat read path.
- Extrapolating synthetic daily prices from `calendar_month` offers or arbitrary non-matching package durations (prohibited by ADR 0010 and ADR 0018).
