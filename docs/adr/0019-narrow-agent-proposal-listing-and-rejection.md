# Narrow Agent Proposal Enumeration and Rejection Without Inventory Mutation Privileges (Extends ADR 0001 & ADR 0017)

Authenticated ingestion agents (`Bearer AGENT_API_KEY`) can enumerate staged Change Proposals via `GET /api/agent/change-proposals` (with deterministic `created_at DESC, id ASC` pagination and exact `totalCount` / `hasMore` / `nextOffset` metadata) and reject individual `pending` proposals via a dedicated `POST /api/agent/change-proposals/[id]/reject` route without weakening `/api/admin/*` session authentication or granting `AGENT_API_KEY` access to `ChangeProposalService.apply` or any live catalog write paths (`motorcycle_rentals`, `rental_offers`, `rental_rate_tiers`, `motorcycle_conditions`, `rental_shops`). Rejection requires an explicit positive integer `expectedVersion` and a non-empty bounded `reason` (accepting `notes` as an alias), claims the proposal atomically via the `'pending' -> 'reviewing'` compare-and-swap lock (`status = 'pending' AND version = expectedVersion`) so concurrent admin approvals and agent rejections cannot overwrite one another, marks only pending actionable `change_proposal_items` as `'rejected'`, leaves historical/applied proposals, admin `unresolved_candidates` decisions (`dismissed`, `excluded`, `resolved_applied`), `shop_agent_configs`, and `crawl_runs` untouched (returning only candidates held in `ready_for_proposal` by that rejected proposal back to `open` with `actor_type = 'agent'`), and appends a non-secret audit record to `proposal_decision_events` (`decision = 'reject'`, `actor_id = NULL`, `metadata = { actorType: 'agent', authMethod: 'agent_api_key', rejectedItemCount }`). Any stale `expectedVersion` or non-`pending` proposal status (including repeated rejection retries after `version` advances to `rejected`) fails deterministically with `409 Conflict` carrying `currentStatus` and `currentVersion` without mutating rows or duplicating decision events.
